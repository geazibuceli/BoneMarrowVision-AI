# Contributing

Thank you for contributing to BoneMarrowVision AI. This is a research and educational project, not a medical device. Contributions must preserve that scope and must not present model outputs as clinical diagnoses.

## Before you start

- Open an issue for significant behavior, API, or model changes.
- Keep source code, documentation, tests, API responses, and interface text in English.
- Do not commit raw data, processed splits, patient identifiers, credentials, uploads, model weights, prediction images, or experiment-tracking stores.
- Commit only deliberately reviewed, de-identified aggregate reports. Remove personal paths and record whether an artifact is historical or was generated by the current provenance format.
- Treat the dataset as a separate asset: follow its CC BY 4.0 attribution requirements and the TCIA access terms.

## Development workflow

1. Create a Python 3.11 environment and install the ML package with `python -m pip install -e "ml[dev]"`.
2. Install backend development dependencies with `python -m pip install -r backend/requirements-dev.txt`.
3. Install frontend dependencies with `cd frontend && npm install`.
4. Start the local stack with `docker compose up --build` when testing API, database, model, or Grad-CAM integration.
5. Add an Alembic revision for every database-schema change; do not rely on runtime `create_all` calls.
6. Run the focused tests and checks before opening a pull request:

```bash
make check
```

## Model and dataset changes

Changes affecting model behavior must document the dataset source and license, split strategy, split-manifest hash, random seed, deterministic settings, configuration, checkpoint hash, hardware, training duration, and evaluation scope. Report accuracy together with class-balanced metrics such as macro F1, and describe limitations for underrepresented classes. Never claim clinical performance without appropriate external validation and expert review.

## Pull requests

Use a concise conventional commit such as `feat: add calibration report`, `fix: validate upload size`, or `test: cover grouped split`. A pull request should explain the problem, summarize the change, list validation commands, and call out any new assumptions or data requirements.
